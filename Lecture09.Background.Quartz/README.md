# Лекция 09 — Quartz.NET

Несколько экземпляров **VideoService** с планировщиком Quartz.NET, которые
запускаются и останавливаются руками в отдельных консолях, в любой момент, и
объединяются в кластер через общую базу **Postgres**. Все узлы регистрируют одни и те же задачи, но каждое
срабатывание выполняется только на одном из них.

## Задачи

| Задача | Расписание | Пример чего |
|---|---|---|
| `StuckVideosCheckJob` — поиск роликов, зависших в обработке | каждую секунду (`SimpleTrigger`) | фиксированный интервал, `[DisallowConcurrentExecution]` |
| `CleanupJob` — удаление черновиков и временных файлов | два cron-триггера: `drafts-cleanup` (`0/5 * * * * ?`) и `temp-files-cleanup` (`2/5 * * * * ?`) | одна задача — несколько расписаний, у каждого триггера свои данные и своё правило misfire |
| `AuthorsReportJob` — отчёт о просмотрах авторам | cron `0/2 * * * * ?` + календарь `quiet-time` | календарь исключений |
| `PublishVideoJob` — публикация ролика | однократно, через 10 секунд после загрузки | отложенная задача, восстановление после падения узла |

Однократные задачи ставит **UploadsSimulator**: каждый узел раз в секунду
"принимает загрузку" ролика и добавляет одноразовый триггер публикации.
Триггер сохраняется в базе, и публикацию выполняет тот узел кластера,
который первым его захватит, — не обязательно тот, что принял загрузку.

Задачи в `Program.cs` оформлены как примеры 1–4, их можно включать и
выключать комментированием. Для примера 4 нужна ещё регистрация
`UploadsSimulator` в конце `Program.cs`. Задачи и триггеры, которые уже
попали в базу, остаются там и после того, как их убрали из кода (см.
"Регистрация на каждом узле" в концепциях), поэтому после изменений в
`Program.cs` базу стоит очистить:

```bash
dotnet run -- cleanup
```

Эта команда удаляет из базы все задачи, триггеры и календари и завершается.

## Концепции

- **Задача отдельно от расписания** — `IJob` описывает, *что* делать,
  `ITrigger` — *когда*. `CleanupJob` зарегистрирована один раз, а запускают
  её два триггера, каждый со своими данными (`UsingJobData("Target", ...)`),
  которые задача читает из `MergedJobDataMap`.
- **Cron в Quartz** — с секундами: `сек мин час день месяц день_недели`.
  `?` — "не задано" (день месяца и день недели нельзя задать одновременно).
  В примере расписания учащены для наглядности, в жизни было бы
  `0 0 3 * * ?` — каждый день в 03:00, или `0 0 9 ? * MON-FRI` — по будням
  в 09:00.
- **Календарь исключений** — `CronCalendar("10-19,30-39,50-59 * * * * ?")`
  исключает каждые вторые 10 секунд минуты: отчёт уходит в :00–:08,
  :20–:28, :40–:48, а в промежутках молчит. В жизни
  это `HolidayCalendar` с праздниками или `WeeklyCalendar` с выходными.
- **Хранение в базе (AdoJobStore)** — задачи, триггеры, календари и
  состояние узлов лежат в таблицах `qrtz_*` и переживают перезапуск. Сам
  создавать схему Quartz.NET 3.x не умеет, поэтому официальный скрипт
  `postgres/tables_postgres.sql` из репозитория Quartz.NET выполняется
  при первом старте контейнера.
- **Кластер** — узлы с одинаковым `SchedulerName` и разными `SchedulerId`
  (`node-<pid>`, печатается при старте). Узел захватывает триггер под блокировкой строки
  в `qrtz_locks` (`SELECT ... FOR UPDATE`), поэтому каждое срабатывание
  выполняется ровно на одном узле. Распределение не равномерное: триггер
  забирает тот узел, который первым за ним пришёл, поэтому одну и ту же
  задачу часто подряд выполняет один и тот же узел.
- **Отметки узлов (check-in)** — каждый узел раз в 2 секунды обновляет свою
  строку в `qrtz_scheduler_state`. Узел, который давно не отмечался,
  считается упавшим: другой узел освобождает захваченные им триггеры, а
  задачи с `RequestRecovery` выполняет заново (`context.Recovering = true`).
- **Misfire** — срабатывание, опоздавшее больше чем на `MisfireThreshold`
  (5 секунд), считается пропущенным, и что с ним делать, решает правило
  триггера:
  - `drafts-cleanup` — `FireAndProceed`: выполнить один раз сразу, дальше
    по расписанию;
  - `temp-files-cleanup` — `DoNothing`: пропустить и ждать следующего
    срабатывания;
  - `authors-report` — правило по умолчанию, для cron это тоже "выполнить
    один раз сразу";
  - `stuck-videos-check` — по умолчанию для повторяющегося `SimpleTrigger`:
    перейти к следующему срабатыванию;
  - публикации — `FireNow`: выполнить, как только поднимется хоть один узел.
- **Регистрация на каждом узле** — все узлы при старте регистрируют одни и
  те же задачи. Первый создаёт их в базе, остальные не перезаписывают
  (`IgnoreDuplicates = true`, `OverWriteExistingData = false`), иначе каждый
  перезапуск узла сбрасывал бы триггеры и время их следующего срабатывания.
  Обратная сторона: изменённое в коде расписание не применится, пока не
  очистить базу.
- **Повторов нет** — если задача упала с исключением, Quartz не повторит её
  сам: повторы и задержки между ними реализуются самостоятельно.

## 1. Запуск Postgres

```bash
docker compose up -d
```

Postgres на `localhost:5432`, база `quartz` (`postgres` / `postgres`).
Таблицы Quartz создаются скриптом при первом старте контейнера:

```bash
docker exec -it lecture09-quartz-postgres psql -U postgres -d quartz -c '\dt'
```

## 2. Запуск узлов

Каждый узел в своей консоли:

```bash
cd Lecture09.Background.Quartz.VideoService
dotnet run
```

Запустите так же ещё два узла. При старте узел печатает свой id `node-<pid>`.

## Остановка

```bash
docker compose down
```
