# Лекция 09 — Hangfire

**UploadService** — сервис приёма видео: страница с кнопками "загрузить
ролик", контроллеры, которые ставят задачи обработки в Hangfire, и панель
мониторинга Hangfire Dashboard. Сам задачи не выполняет. **Worker** — сервер
Hangfire, который забирает задачи из хранилища и выполняет их; запускается
руками в нескольких консолях, в любой момент. Все они работают с одной базой
**Postgres**, брокер не нужен. **Contracts** — интерфейс задач `IVideoJobs`,
общий для UploadService и Worker.

## Как устроен Hangfire

```
 UploadService (клиент)            Postgres (схема hangfire)             Worker × N (серверы)
 ──────────────────────            ─────────────────────────             ────────────────────
 Enqueue / Schedule /     ──────►  job       — вызов метода + JSON  ◄──  опрос очереди
 ContinueJobWith /                 jobqueue  — очередь задач            ↓
 AddOrUpdate                       state     — история состояний        вызов метода VideoJobs
                                   set/hash  — расписания, повторы      ↓
 Dashboard (/hangfire)    ◄──────  server    — живые Worker'ы       ──► Succeeded / Failed
```

- **Задача — это вызов метода.** `Enqueue<IVideoJobs>(x => x.ValidateAsync(...))`
  не выполняет метод, а сохраняет в базу тип, имя метода и аргументы в JSON.
- **Клиент** (UploadService) только записывает задачи. Ему нужна база и
  интерфейс, реализация не нужна.
- **Сервер** (Worker) — процесс с `AddHangfireServer`. Его потоки опрашивают
  очередь, забирают задачу, создают реализацию `IVideoJobs` из DI и вызывают
  метод. Результат пишется в базу.
- **Dashboard** читает те же таблицы и показывает всё, что происходит.

Подробные комментарии — в `Program.cs` обоих проектов, в `IVideoJobs` и
`VideoJobs`.

## Задачи

На каждую загрузку UploadService ставит:

| Задача | Вид | Как ставится |
|---|---|---|
| `ValidateAsync` — проверка файла | разовая (fire-and-forget) | `Enqueue` |
| `TranscodeAsync` 1080p → 720p → 480p — перекодирование | продолжения, очередь `transcoding`, 3 попытки | `ContinueJobWith` |
| `PublishAsync` — публикация | продолжение | `ContinueJobWith` |
| `DeleteOriginalAsync` — удаление исходного файла | отложенная, через 60 секунд | `Schedule` |

Кроме того, при старте UploadService регистрирует периодическую задачу
`RecalculateStatisticsAsync` — пересчёт статистики просмотров каждые 10
секунд (`AddOrUpdate`, cron `*/10 * * * * *`, первое поле — секунды). Кнопка
"Пересчитать сейчас" запускает её вне расписания (`Trigger`).

Полезная нагрузка — сообщения в логе Worker'а и `Task.Delay`.
Перекодирование длится 5 секунд и с вероятностью 20% падает.

## Концепции

- **Интерфейс — контракт между процессами** — UploadService знает только
  `IVideoJobs`, Worker — его реализацию. Переименование интерфейса или метода
  ломает задачи, которые уже лежат в базе.
- **Хранилище — обычная база** — `Hangfire.PostgreSql` сам создаёт схему
  `hangfire` при первом подключении.
- **Очереди и число обработчиков** — `[Queue("transcoding")]` на методе
  интерфейса отправляет перекодирование в отдельную очередь. Каждый Worker
  обслуживает очереди из `options.Queues` (по порядку приоритета, здесь
  `transcoding`, `default`) и выполняет `options.WorkerCount` задач
  параллельно (здесь 2). Так перекодированию
  можно выделить десять обработчиков, а проверке — один.
- **Продолжения** — `ContinueJobWith` ставит задачу в состояние `Awaiting`,
  и она попадает в очередь, только когда родительская завершилась успешно.
  Цепочка линейная: три качества можно было бы перекодировать параллельно,
  но дождаться завершения всех трёх (batches) можно только в платной
  Hangfire Pro.
- **Автоматические повторы** — по умолчанию 10 попыток с растущей
  задержкой. У `TranscodeAsync` своя политика:
  `[AutomaticRetry(Attempts = 3, DelaysInSeconds = [5, 10, 20])]`. После
  последней попытки задача переходит в `Failed`, а её продолжения ждут; если
  перезапустить её вручную из панели, цепочка продолжится.
- **Опрос** — Worker проверяет очередь раз в `QueuePollInterval`, а
  отложенные, повторяемые и периодические задачи — раз в
  `SchedulePollingInterval`. По умолчанию оба интервала 15 секунд, в
  примере — 1 секунда.
- **Хотя бы один раз** — при штатной остановке Worker'а (Ctrl+C) прерванная
  задача сразу возвращается в очередь. Если процесс убит, задача остаётся
  "захваченной" упавшим Worker'ом и становится видна остальным через
  `InvisibilityTimeout` (30 секунд). В обоих случаях задача выполняется
  повторно, поэтому должна быть идемпотентной.
- **Периодические задачи в кластере** — каждый Worker проверяет расписание,
  но ставит очередное выполнение под распределённой блокировкой в базе,
  поэтому каждое срабатывание попадает в очередь один раз.

## 1. Запуск Postgres

```bash
docker compose up -d
```

Postgres на `localhost:5432`, база `hangfire` (`postgres` / `postgres`).

## 2. Запуск UploadService

```bash
cd Lecture09.Background.Hangfire.UploadService
dotnet run
```

- Страница с кнопками: [http://localhost:5080](http://localhost:5080) —
  загрузить один ролик (своё название или случайное), загрузить 10 роликов,
  пересчитать статистику. Сверху — счётчики задач по состояниям и число
  живых Worker'ов, ниже — загруженные ролики со ссылками на их задачи в
  Dashboard.
- Dashboard: [http://localhost:5080/hangfire](http://localhost:5080/hangfire).

Запускайте его первым: при первом подключении он создаст схему `hangfire`.
Если запустить всё одновременно, схему начнут создавать несколько процессов,
и один из них напишет в лог ошибку — это не мешает работе.

## 3. Запуск Worker'ов

Каждый Worker в своей консоли:

```bash
cd Lecture09.Background.Hangfire.Worker
dotnet run
```

При старте Worker печатает своё имя `worker-<pid>` — то же имя видно в
Dashboard на вкладке `Servers`.

## Остановка

```bash
docker compose down
```
