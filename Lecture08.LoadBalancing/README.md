# Лекция 08 — Балансировка нагрузки

**LoadGenerator** с заданной скоростью шлёт запросы в **HAProxy**, а HAProxy
раскидывает их между несколькими инстансами **CatsService**, которые
запускаются руками в отдельных консолях.

В HAProxy настроены два входа на одни и те же инстансы:

| Адрес | Backend | Что делает |
|---|---|---|
| `localhost:8080` | `cats-static` | статический алгоритм + проверка L4 (TCP) |
| `localhost:8081` | `cats-dynamic` | динамический алгоритм + проверка L7 (`GET /health`) |

Переключаться между ними — просто другой `Url` у генератора. Можно
запустить два генератора одновременно и сравнивать вживую.

## Концепции

- **Единая точка входа** — генератор знает только адрес балансировщика.
  Сколько за ним инстансов и где они, он не знает.
- **Кто ответил** — каждый инстанс добавляет в ответ заголовок
  `X-Instance`. Генератор раз в секунду печатает, сколько ответов пришло
  от каждого инстанса, среднее время ответа, число ошибок и сколько
  запросов сейчас "в полёте":

  ```
  cats-1: 100 req, 20 ms | cats-2: 100 req, 19 ms | cats-3: 100 req, 19 ms | errors: 0 | in flight: 0
  ```

  А каждый инстанс в своей консоли печатает, сколько запросов он
  обработал за секунду.
- **Генератор не ждёт ответов** — запросы уходят с постоянной скоростью
  `RequestsPerSecond` независимо от того, как быстро отвечают инстансы
  (как producer в лекции 04). Медленный инстанс копит незавершённые
  запросы — их видно в `in flight`.
- **Статические алгоритмы** (`cats-static`) — выбирают инстанс по
  заранее заданному правилу:
  - `roundrobin` — по кругу;
  - `roundrobin` + `weight N` у серверов — взвешенный;
  - `random` — случайный инстанс;
  - `source` — хэш IP клиента. У генератора один IP, поэтому весь трафик
    уйдёт на один инстанс: это та самая проблема "клиентов за общим NAT".
- **Динамические алгоритмы** (`cats-dynamic`) — смотрят на состояние
  инстансов:
  - `leastconn` — запрос уходит инстансу с наименьшим числом активных
    соединений. Медленный инстанс дольше держит соединения, поэтому
    автоматически получает меньше запросов;
  - `random(2)` — Power of Two Choices: берём два случайных инстанса и
    отдаём запрос менее загруженному.
- **Алгоритм и проверки независимы** — алгоритм выбирает, кому из
  *доступных* инстансов отдать запрос, а список доступных формируют
  health check'и. Проверки работают с любым алгоритмом, в том числе со
  статическим.
- **Активная проверка** — HAProxy сам раз в секунду проверяет каждый
  инстанс (`check` у серверов). 2 неудачи подряд — инстанс исключён,
  2 успеха — возвращён. Бывает двух уровней:
  - **L4** (`cats-static`) — просто открыть TCP-соединение. Замечает
    упавший процесс, но не замечает живой процесс, который отвечает
    ошибками;
  - **L7** (`cats-dynamic`, `option httpchk`) — вызвать `GET /health` и
    проверить статус ответа. Замечает и то, и другое.
- **Пассивная проверка (outlier detection)** — HAProxy смотрит на ответы
  на настоящие запросы (`observe layer7`): 10 ошибок подряд — инстанс
  исключён. Лишних запросов нет, но проблему замечают только после того,
  как реальные запросы уже пострадали.
- **Health check в инстансе** — стандартный механизм ASP.NET Core:
  `AddHealthChecks().AddCheck<InstanceHealthCheck>()` и
  `MapHealthChecks("/health")`. Отвечает `Healthy` (200) или
  `Unhealthy` (503).
- **Сломать инстанс** — `POST /health/toggle` переключает инстанс в
  "сломанное" состояние: `/health` отвечает 503, а обычные запросы — 500.
  Процесс при этом жив. Повторный вызов чинит.
- **L7 и L4** — `mode http` (L7): HAProxy разбирает каждый HTTP-запрос
  и балансирует запросы. `mode tcp` (L4): HAProxy не смотрит внутрь и
  балансирует TCP-соединения.

## 1. Запуск HAProxy

```bash
docker compose up -d
```

- Статический вход: [http://localhost:8080](http://localhost:8080)
- Динамический вход: [http://localhost:8081](http://localhost:8081)
- Страница статистики: [http://localhost:8404](http://localhost:8404) —
  оба backend'а, состояние каждого сервера (UP/DOWN), запросы в секунду,
  ошибки. Обновляется раз в секунду. Включён режим администратора:
  отметьте сервер галочкой и выберите внизу `Set state to DRAIN` (не
  получает новых запросов) или `MAINT` (выключен) — так можно убирать
  инстансы из ротации прямо из UI, `READY` возвращает обратно.

Конфиг лежит в `haproxy/haproxy.cfg`, все варианты алгоритмов и проверок
расписаны в нём комментариями. После правки применяем его без перезапуска
контейнера:

```bash
docker kill -s HUP lecture08-haproxy
```

HAProxy работает в `network_mode: host`, чтобы достучаться до инстансов,
запущенных через `dotnet run` на `127.0.0.1`. На Docker Desktop
(Mac/Windows) host networking нужно включить в Settings → Resources →
Network.

## 2. Запуск инстансов

Каждый инстанс в своей консоли. Номер задаёт имя (`cats-N`) и порт
(`5100 + N`), в `haproxy.cfg` прописаны `cats-1`...`cats-3`:

```bash
cd Lecture08.LoadBalancing.CatsService
dotnet run -- --Instance:Number=1
```

```bash
dotnet run -- --Instance:Number=2
dotnet run -- --Instance:Number=3
```

## 3. Запуск генератора нагрузки

```bash
cd Lecture08.LoadBalancing.LoadGenerator

# статический backend (по умолчанию)
dotnet run -- --LoadGenerator:RequestsPerSecond=300

# динамический backend
dotnet run -- --LoadGenerator:RequestsPerSecond=300 --LoadGenerator:Url=http://localhost:8081/cats/1
```

### Динамическая балансировка (`:8081`)

Перезапустите второй инстанс медленным и запустите два генератора — на
`:8080` и на `:8081`:

```bash
dotnet run -- --Instance:Number=2 --Instance:DelayMs=300
```

1. **Статический vs динамический** — round robin всё равно отдаёт
   медленному `cats-2` треть запросов, а leastconn — в несколько раз
   меньше:

   ```
   :8080 roundrobin: cats-1: 100 req, 19 ms | cats-2: 100 req, 299 ms | cats-3: 99 req, 19 ms
   :8081 leastconn:  cats-1: 130 req, 20 ms | cats-2:  38 req, 299 ms | cats-3: 131 req, 20 ms
   ```

2. **Power of Two Choices** — `balance random(2)` в `cats-dynamic`: почти
   то же, что `leastconn`, но без знания о всех инстансах сразу.
3. **Активная проверка** — "сломайте" инстанс:

   ```bash
   curl -X POST http://localhost:5103/health/toggle
   ```

   На `:8081` через ~2 секунды `cats-3` исключён, ошибок нет. На `:8080`
   он продолжает получать треть запросов, и все они падают с 500: процесс
   жив и принимает соединения, поэтому L4-проверку проходит. На странице
   статистики `cats-3` в `cats-dynamic` — DOWN (`L7STS`, неверный статус
   ответа), в `cats-static` — UP (`L4OK`). Почините тем же запросом —
   через 2 секунды он вернётся.
4. **Упавший инстанс** — остановите `cats-1` (Ctrl+C). На `:8081` ошибки
   идут, только пока проверка не заметит (1–2 секунды), дальше трафик
   делят оставшиеся. Запустите снова — он сам вернётся в ротацию.
5. **Пассивная проверка** — в `cats-dynamic` закомментируйте
   `option httpchk` и раскомментируйте строку с `observe layer7`,
   "сломайте" инстанс. После 10 ошибок подряд он исключается, но
   TCP-проверку процесс проходит, поэтому через пару секунд HAProxy
   пробует вернуть его, снова получает 10 ошибок, и так по кругу — в
   генераторе видны периодические всплески ошибок.
6. **Redispatch** — раскомментируйте `retries 1` и `option redispatch` и
   остановите инстанс: запросы, не дошедшие до него, уходят на соседей, и
   клиент ошибок почти не видит.

## Остановка

```bash
docker compose down
```
