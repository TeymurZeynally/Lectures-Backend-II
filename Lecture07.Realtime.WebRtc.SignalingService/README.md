# Лекция 07 — WebRTC

Два браузера обмениваются видео, аудио и файлами напрямую, без сервера
посередине. Сервер нужен только для того, чтобы они нашли друг друга
(**signaling**), и, если напрямую никак, для пересылки трафика (**TURN**).

- **Видеозвонок** (`call.html`) — камера + микрофон или экран.
- **Передача файлов** (`files.html`) — байты через DataChannel с
  отображением скорости.

## Концепции

- **Signaling** — WebRTC не говорит, как браузерам обменяться
  описаниями соединения, это делаем мы. Здесь это WebSocket
  `/signaling/rooms/{room}`: в комнате максимум двое, сервер ничего не
  разбирает и просто пересылает сообщения второму участнику. Когда
  приходит второй, первый получает `peer-joined` и начинает обмен:
  1. первый отправляет **offer** (SDP: какие треки, кодеки, ключи);
  2. второй отвечает **answer**;
  3. оба по мере нахождения шлют друг другу **ICE-кандидаты** — адреса,
     по которым до них можно попробовать достучаться.

  Вся эта логика в `wwwroot/rtc.js`, она общая для обеих страниц.
- **ICE-кандидаты** — после соединения на странице видно, какая пара
  кандидатов выбрана:
  - `host` — локальный адрес сетевой карты, прямое соединение;
  - `srflx` — публичный адрес, который браузер узнал у **STUN**-сервера
    ("как меня видно снаружи NAT"). Трафик всё равно идёт напрямую;
  - `relay` — адрес на **TURN**-сервере. Весь трафик идёт через него,
    это работает, даже когда прямое соединение невозможно (симметричный
    NAT, корпоративный firewall).
- **STUN vs TURN** — список ICE-серверов страница получает с сервера
  (`GET /signaling/ice-servers?mode=stun|turn`, значения в
  `appsettings.json`), чтобы не хранить пароль от TURN в JS. В режиме
  TURN включается `iceTransportPolicy: "relay"`: браузеру запрещено
  соединяться напрямую, поэтому трафик гарантированно пойдёт через TURN.
  В режиме STUN на одной машине почти всегда будет выбран `host` — чтобы
  увидеть `srflx`, нужны две разные сети (например, ноутбук и телефон
  через мобильный интернет).
- **Медиа** — `getUserMedia` (камера + микрофон) или `getDisplayMedia`
  (экран). Треки добавляются в соединение до offer'а, второй участник
  получает их в `ontrack`.
- **DataChannel** — произвольные байты по тому же соединению. Канал
  создаётся `negotiated: true` с одинаковым `id` на обеих сторонах.
  Файл отправляется JSON-заголовком `{name, size}` и затем кусками по 64
  КБ. `bufferedAmount` не даёт залить в буфер больше, чем успевает уйти в
  сеть, иначе канал закроется.

## 1. Запуск TURN-сервера

```bash
cd Lecture07.Realtime.WebRtc.SignalingService
docker compose up -d
```

Поднимается [coturn](https://github.com/coturn/coturn) на `localhost:3478`
(логин и пароль `student` / `student`, порты для relay 49160-49200).
TURN раздаёт браузерам relay-адреса, поэтому контейнер работает в
`network_mode: host`. На Docker Desktop (Mac/Windows) host networking нужно
включить в Settings → Resources → Network.

Для режима STUN docker не нужен — используется публичный
`stun.l.google.com`.

## 2. Запуск сервиса

```bash
dotnet run
```

Откройте [http://localhost:5072](http://localhost:5072) в двух вкладках
(или двух браузерах), выберите одну и ту же комнату и режим и нажмите
"Подключиться" в обеих. Логи coturn (`docker logs -f lecture07-coturn`)
покажут, что в режиме TURN трафик действительно идёт через него.

Несколько замечаний:

- Камера и экран доступны браузеру только на `localhost` или по HTTPS.
  Для подключения с другого устройства нужен HTTPS, а в
  `appsettings.json` вместо `localhost` — адрес машины с TURN.
- Две вкладки на одной машине с микрофоном дадут эхо — используйте
  наушники или режим "Экран".
- Если один из участников перезагрузил страницу, перезагрузите обе.

## Остановка

```bash
docker compose down
```
