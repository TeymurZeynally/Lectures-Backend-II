# Лекция 04 — NATS (JetStream)

Минимальный пример на NATS: один **Producer**, который заливает поток
событий "кота покормили" в JetStream, и **Consumer**, который можно
запускать в нескольких экземплярах, чтобы увидеть, как durable consumer
делит между ними работу.

По умолчанию используется **JetStream** — персистентный слой NATS. Именно
он делает возможной демонстрацию "один consumer не успевает, добавляем
второго — backlog разгребается быстрее", как и в примерах с Kafka и
RabbitMQ из этой серии. Оба приложения также умеют работать в режиме
обычного **core NATS** (`--Mode=Core`, см. ниже) вообще без персистентности
— чтобы показать, чем именно приходится жертвовать без JetStream: ни
stream, ни ack, а любое сообщение, опубликованное пока никто не подписан,
теряется безвозвратно.

## Концепции

- **Stream и subject** — JetStream - надстройка над NATS, добавляющая
  сохранение сообщений на диск там, где базовый NATS ничего не хранит.
  Включается на стороне сервера и не требует изменений в коде отправителей:
  stream прозрачно перехватывает всё, что публикуется в заданные им subject,
  и складывает в упорядоченный лог с настраиваемой политикой хранения — по
  времени, размеру, количеству сообщений или до подтверждения обработки.

  Оперирует двумя сущностями: stream — хранилище, захватывающее один или
  несколько subject-паттернов, и consumer — объект на сервере с собственной
  позицией чтения и фильтром по subject, через который сервисы читают
  накопленное. Сообщения не удаляются после прочтения, поэтому разные
  consumer читают один и тот же лог независимо, каждый со своей позиции.

  В этом примере producer публикует в subject `cat.feedings`, который
  захватывается stream'ом `CAT_FEEDINGS`. Оба сервиса объявляют stream при
  старте, так что он появится независимо от того, кто запустился первым.
- **Durable consumer и конкурирующие pull'ы** — каждый экземпляр Consumer
  подключается к одному и тому же durable consumer (`DurableConsumerName`).
  Любое количество процессов может одновременно забирать сообщения из
  одного durable consumer, и JetStream распределяет сообщения между ними —
  это аналог consumer group в Kafka или конкурирующих потребителей одной
  очереди в RabbitMQ.
- **Prefetch (`MaxMsgs`)** — каждый pull-запрос забирает не больше
  `PrefetchCount` сообщений за раз (по умолчанию 1). Это аналог QoS
  prefetch в RabbitMQ: без него первый подключившийся consumer жадно
  захватывает большую пачку ещё не подтверждённых сообщений себе, а
  второму достаются только остатки — вместо честного деления backlog'а
  пополам. Увеличьте `PrefetchCount`, чтобы увидеть этот эффект.
- **Явный ack** — consumer подтверждает каждое сообщение только после
  "обработки" (`DelayMs`). Неподтверждённое сообщение будет доставлено
  повторно (тому, кто следующим запросит pull), если consumer умрёт до
  того, как успеет его подтвердить.

## 1. Запуск брокера

```bash
docker compose up -d
```

Поднимаются:
- **NATS** с включённым JetStream на `localhost:4222`, HTTP-мониторинг на
  `localhost:8222`
- **NATS UI** ([NUI](https://github.com/nats-nui/nui)) на
  [http://localhost:31311](http://localhost:31311) — можно смотреть
  streams, consumer'ов и сообщения прямо в браузере. При первом открытии
  нужно вручную добавить подключение на `nats://nats:4222` (NUI общается с
  брокером внутри сети compose, а не через `localhost`).

Сам NATS-сервер не требует никакой настройки — донастроить вручную нужно
только UI, один раз.

## 2. Запуск Producer

```bash
cd Lecture04.Async.Nats.Producer
dotnet run
```

Публикует в subject `cat.feedings` со скоростью `MessagesPerSecond`
(по умолчанию 50) без остановки. При старте создаёт stream `CAT_FEEDINGS`,
если его ещё нет.

Настройки можно переопределить через аргументы командной строки (они
переопределяют `appsettings.json`):

```bash
# публиковать намного быстрее, чтобы накопить заметный backlog
dotnet run -- --Processing:MessagesPerSecond=2000
```

## 3. Запуск одного или нескольких Consumer

Каждый терминал ниже — отдельный **экземпляр consumer**, читающий из
одного и того же durable consumer. Дайте каждому свой `InstanceName`, чтобы
различать их в логах:

```bash
cd Lecture04.Async.Nats.Consumer
dotnet run -- --Processing:InstanceName=consumer-1
```

Открывайте больше терминалов для новых экземпляров:

```bash
dotnet run -- --Processing:InstanceName=consumer-2
dotnet run -- --Processing:InstanceName=consumer-3
```

С одним consumer'ом и не самым маленьким `DelayMs` он не успевает за
producer'ом и начинает отставать — stream просто хранит накопившийся
backlog (смотрите `stream-seq` в логах или количество сообщений в NUI).
Запустите второй экземпляр — и в логах обоих consumer'ов пойдут
чередующиеся, почти последовательные номера stream-seq: backlog разгребается
вдвое быстрее, потому что JetStream делит его между ними.

Другие полезные переопределения:

```bash
# смоделировать более медленную обработку сообщения, чтобы один consumer отставал
dotnet run -- --Processing:DelayMs=300

# поднять prefetch, чтобы увидеть, как один consumer захватывает всю пачку вместо честного деления
dotnet run -- --Processing:PrefetchCount=50

# запустить второй, независимый durable consumer, который сам читает весь stream с начала
dotnet run -- --Processing:DurableConsumerName=analytics --Processing:InstanceName=analytics-1
```

## 4. Режим Core NATS (без персистентности)

Передайте `--Mode=Core` и Producer, и Consumer, чтобы переключиться на
обычный core NATS pub/sub вместо JetStream — без stream, без хранимого
backlog, без ack. Consumer'ы в одной `QueueGroup` по-прежнему конкурируют за
сообщения так же, как и раньше (это не специфика JetStream), но теперь это
по-настоящему fire-and-forget:

```bash
cd Lecture04.Async.Nats.Producer
dotnet run -- --Mode=Core
```

```bash
cd Lecture04.Async.Nats.Consumer
dotnet run -- --Mode=Core --Processing:InstanceName=consumer-1
```

Запустите Producer первым и дайте ему поработать какое-то время *до*
запуска любого Consumer: все сообщения, опубликованные до того, как
consumer подписался, просто исчезают — в отличие от режима JetStream выше,
разгребать тут нечего. Лог Consumer'а начнётся с того места, где в этот
момент находится трафик subject'а (сравните номер `seq`, с которого он
стартует, с тем, сколько сообщений Producer уже успел опубликовать).

Это и есть компромисс core NATS против JetStream в одной демонстрации:
JetStream стоит вам stream'а, durable consumer'а и явных ack'ов, но взамен
даёт поведение backlog/replay из раздела 3; в core NATS нет всей этой
церемонии, но медленный или отсутствующий consumer просто теряет данные.

## Остановка

```bash
docker compose down
```
